# Requerimientos de Arquitectura y Despliegue (Docker)

## Estructura del Repositorio
El proyecto se mantendrá como un **Monorepo** (un único repositorio) que contendrá tanto el código del Frontend como el del Backend, incluyendo la base de datos y los microservicios. Esto facilitará el despliegue orquestado mediante Docker Compose.

## Arquitectura de Contenedores
Se aplicará el principio de "un proceso por contenedor", separando los servicios de manera independiente para garantizar escalabilidad, tolerancia a fallos y facilidad de actualización.

La arquitectura consta de **6 contenedores independientes** corriendo en una misma red virtual de Docker:

1. **Contenedor Frontend**: Alojará la aplicación cliente (Next.js).
2. **Contenedor API Gateway**: Enrutador de tráfico y validador JWT central (Spring Cloud Gateway).
3. **Contenedor App Principal (Backend Core)**: Contiene la lógica central del servidor.
4. **Contenedor MS Asistencias**: Servicio dedicado a la gestión de asistencias.
5. **Contenedor MS Calificaciones (ms-notas)**: Servicio dedicado a la gestión de notas.
6. **Contenedor Base de Datos**: Servidor MySQL único que aloja esquemas lógicos separados para el Core y cada MS (`backoffice_itec`, `db_asistencias`, `db_calificaciones`).

## Estructura del Repositorio (Código Fuente)
El código fuente está distribuido de la siguiente manera en la raíz del repositorio para independizar los ciclos de vida de cada servicio:

```text
/
├── /api-gateway       (Contenedor 2: Spring Cloud Gateway)
├── /ms-asistencias    (Contenedor 4: Microservicio Asistencias)
├── /ms-notas          (Contenedor 5: Microservicio Calificaciones)
├── /frontend          (Contenedor 1: App Next.js)
│
└── /backend           (POM Padre Multi-módulo de Java)
    ├── /api           (Aplicación Spring Boot del Core: arranque, config, migraciones)
    ├── /commons       (Librería compartida, también la usan los MS. No dockerizado)
    ├── /security      (Spring Security, login y JWT. No dockerizado)
    ├── /core          (Dominio académico: modelo, servicios, controllers)
    ├── pom.xml        (POM raíz del ecosistema core)
    └── Dockerfile     (Construcción del Contenedor 3)
```

## Orquestación
- Se utiliza un archivo `docker-compose.yml` en la raíz del proyecto (que hace un `include` al compose interno del backend) para levantar y conectar todo con el comando `docker compose up`.
- Los microservicios se comunican entre sí y con la base de datos a través de la red interna de Docker usando los nombres declarados de los servicios (ej. `http://backend-app:8082` o `jdbc:mysql://mysql-db:3306/...`).

## Estrategia de Comunicación: API Gateway y Frontend

> Revisado 2026-11-06 contra `docker-compose.yml`, `backend/docker-compose.yml` y `frontend/lib/api-server.ts` (pendiente #31).

El navegador **nunca** llama al backend: el frontend usa Server Components y Server Actions, así que las peticiones al Gateway salen del **servidor de Next.js**, dentro de la red de Docker. El Gateway decide, según la URL (`/api/v1/<recurso>`), a qué contenedor reenviar la petición.

### Red y puertos
- Todos los contenedores comparten la red por defecto de Docker Compose y se alcanzan por nombre de servicio (`api-gateway`, `backend-app`, `ms-asistencias`, `ms-notas`, `mysql-db`).
- Puertos publicados al host en el entorno local: `3000` (frontend), `8080` (Gateway), `8082` (Core, perfil `local`), `8083` (ms-asistencias), `8084` (ms-notas) y `3306` (MySQL). Se publican para depurar; el contrato es que el frontend solo use el Gateway (constitución C2.5).
- Puerto del Core: `8082` con el perfil `local` (el de `backend/.env.example`, `APP_PROFILE=local`) y `8081` con el perfil `prod`. El Gateway lo recibe en `CORE_API_URL`.

### URLs del frontend
| Variable | Valor en Docker | Quién la usa |
|---|---|---|
| `API_URL` | `http://api-gateway:8080` | Server Components y Server Actions (`getApiBaseUrl()` en `lib/api-server.ts`). Se lee en **runtime**, no en el build. |
| `NEXT_PUBLIC_API_URL` | `http://localhost:8080` | Respaldo cuando no hay `API_URL` (ej. `npm run dev` fuera de Docker, desde `frontend/.env.local`). |

Si ninguna está definida, el frontend usa `http://localhost:8080`. En producción alcanza con apuntar `API_URL` al Gateway interno; no hace falta reconstruir la imagen para cambiar la URL.

### Secretos compartidos
`api-gateway`, `backend-app`, `ms-asistencias` y `ms-notas` deben recibir el mismo `JWT_SECRET`: el Core firma los tokens, el Gateway los valida y los MS firman sus tokens internos para llamar al Core.

### Schema de las bases
- **Core:** con el perfil `local` (el de Docker) Hibernate crea y actualiza el schema (`ddl-auto: update`, Flyway deshabilitado). El perfil `prod` usa Flyway + `ddl-auto: validate`, pero la migración base todavía no está alineada con las entidades (pendiente #45).
- **MS:** arrancan con `DB_DDL_AUTO=update` y crean sus tablas en `db_asistencias` y `db_calificaciones` (`createDatabaseIfNotExist=true`).
