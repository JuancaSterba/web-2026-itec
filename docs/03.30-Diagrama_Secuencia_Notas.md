# Diagrama de Secuencia: Registro de Calificaciones y Cierre de Cursada

Este diagrama ilustra el flujo implementado (2026-07-12) para el registro de calificaciones (microservicio `ms-notas`) y el cálculo automático de la condición final del alumno (Core), cumpliendo con la validación de fechas de cursada y comunicación interservicios.

## 1. Registro de Calificación Parcial o Final

El profesor registra una nota en `ms-notas`. Para asegurar consistencia, el microservicio valida internamente contra el Core que la fecha coincida con un día de cursada real (excepto en exámenes finales).

```mermaid
sequenceDiagram
    autonumber
    actor Profesor
    participant Frontend
    participant Gateway
    participant MS_Notas as ms-notas
    participant Core as Core Backend
    participant DB_Notas as DB Notas

    Profesor->>Frontend: Ingresa nota, tipo (PARCIAL/FINAL)<br>y fecha
    Frontend->>Gateway: POST /api/calificaciones
    Gateway->>MS_Notas: Rutea (inyecta X-User-Roles)
    
    activate MS_Notas
    
    alt tipo == PARCIAL
        MS_Notas->>MS_Notas: Genera JWT interno<br>(InternalTokenService)
        MS_Notas->>Core: GET /api/core/comisiones/{id}/horarios
        Core-->>MS_Notas: Lista de días de cursada
        MS_Notas->>MS_Notas: Valida que la 'fecha' coincida<br>con un día de cursada
    end
    
    MS_Notas->>DB_Notas: Guarda CalificacionParcial
    DB_Notas-->>MS_Notas: OK
    MS_Notas-->>Gateway: 201 Created
    Gateway-->>Frontend: 201 Created
    deactivate MS_Notas
```

## 2. Cierre de Cursada (Cálculo Automático)

El profesor o administrador solicita cerrar la cursada. El Core asume la responsabilidad de contactar a `ms-notas` para recolectar el historial y calcular la situación definitiva del alumno según la modalidad de la materia.

```mermaid
sequenceDiagram
    autonumber
    actor Docente as Profesor / Admin
    participant Frontend
    participant Gateway
    participant Core as Core (CondicionCursadaService)
    participant MS_Notas as ms-notas
    participant DB_Core as DB Core

    Docente->>Frontend: Clic en "Cerrar cursada"
    Frontend->>Gateway: POST /api/core/cursadas/{id}/cerrar
    Gateway->>Core: Rutea
    
    activate Core
    Core->>MS_Notas: GET /api/calificaciones?cursadaId={id}
    Note right of Core: Se envía X-User-Roles para<br>autorización interservicio
    MS_Notas-->>Core: Lista de notas (PARCIAL, FINAL)
    
    Core->>Core: Calcula promedio de Parciales
    
    alt Promedio < 4 (o inasistencias excesivas)
        Core->>Core: condicion = LIBRE
    else Promedio 4 - 6.99
        Core->>Core: condicion = REGULAR
    else Promedio >= 7
        alt Modalidad == PROMOCIONAL
            Core->>Core: condicion = PROMOCIONADA
        else Modalidad == FINAL
            Core->>Core: condicion = REGULAR
        end
    end
    
    opt Tiene nota FINAL registrada
        alt nota FINAL >= 4 y condicion previa == REGULAR
            Core->>Core: condicion = APROBADA
        else nota FINAL < 4 y condicion previa == REGULAR
            Core->>Core: condicion = REGULAR (se mantiene)
        else condicion previa == LIBRE
            Core->>Core: condicion = LIBRE (no se sobreescribe)
        end
    end
    
    Core->>DB_Core: UPDATE cursadas SET condicion_final, nota_cierre
    DB_Core-->>Core: OK
    Core-->>Gateway: 200 OK (Cursada actualizada)
    Gateway-->>Frontend: 200 OK
    deactivate Core
```

### Reglas de Diseño Implementadas
- **Seguridad Interservicio Mixta**: El Core consulta a `ms-notas` pasándole de forma confiable el rol del usuario original (`X-User-Roles`). Sin embargo, cuando `ms-notas` necesita consultar al Core (para validar horarios), se utiliza un mecanismo de **JWT Interno** (con `JWT_SECRET` compartido).
- **Separación de Responsabilidades**: `ms-notas` es responsable exclusivo del almacenamiento CRUD de las notas. `Core` es el dueño de la lógica de negocio académica (promedios, modalidad, transiciones de estado) y orquesta el cierre de la cursada.
