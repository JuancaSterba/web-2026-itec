# Diagrama de Secuencia: Calificaciones, Cierre de Cursada y Cierre de Mesa

> Revisado 2026-11-06 contra el código (pendiente #31). La versión anterior (2026-07-12) mezclaba parciales y finales en `CalificacionParcial` y cerraba la cursada solo con las notas. Hoy los parciales y las notas de mesa son entidades distintas en `ms-notas`, y el cierre de cursada consulta primero la asistencia (spec 002).

## 1. Registro de una calificación parcial

El profesor carga los parciales de una cursada en `ms-notas`. El servicio admite como máximo **3 parciales por cursada**. No valida la fecha contra los horarios de la comisión (eso solo lo hace `ms-asistencias`).

```mermaid
sequenceDiagram
    autonumber
    actor Profesor
    participant Next as Next.js (Server Action)
    participant Gateway
    participant MS_Notas as ms-notas
    participant DB_Notas as db_calificaciones

    Profesor->>Next: Ingresa instancia, nota y fecha
    Next->>Gateway: POST /api/v1/calificaciones-parciales (Bearer JWT)
    Gateway->>Gateway: Valida JWT, inyecta X-User-Roles
    Gateway->>MS_Notas: POST /api/calificaciones-parciales

    activate MS_Notas
    MS_Notas->>MS_Notas: RoleGuard: ADMIN, ADMINISTRATIVO o PROFESOR
    MS_Notas->>DB_Notas: countByCursadaId(cursadaId)
    alt ya hay 3 parciales
        MS_Notas-->>Gateway: 400 "Ya se cargaron los 3 parciales"
    else menos de 3
        MS_Notas->>DB_Notas: save(CalificacionParcial)
        MS_Notas-->>Gateway: 201 Created
    end
    deactivate MS_Notas
    Gateway-->>Next: respuesta
```

## 2. Cierre de cursada (cálculo automático)

El administrativo (o el profesor) previsualiza y cierra la cursada. El Core orquesta: pide la asistencia a `ms-asistencias` y los parciales a `ms-notas`, y calcula la condición según la modalidad de la materia (`CondicionCursadaService`). El detalle del lado de la asistencia está en [`03.20-Diagrama_Secuencia_Asistencia.md`](./03.20-Diagrama_Secuencia_Asistencia.md).

```mermaid
sequenceDiagram
    autonumber
    actor Docente as Administrativo / Profesor
    participant Next as Next.js (Server Action)
    participant Gateway
    participant Core as Core (CondicionCursadaService)
    participant MS_Asis as ms-asistencias
    participant MS_Notas as ms-notas
    participant DB_Core as backoffice_itec

    Docente->>Next: Clic en "Cerrar cursada"
    Next->>Gateway: POST /api/v1/cursadas/{id}/cerrar
    Gateway->>Core: POST /api/cursadas/{id}/cerrar

    activate Core
    alt cursada ya cerrada (condicionFinal != null)
        Core-->>Gateway: 409 "La cursada ya está cerrada"
    else cursada abierta
        Core->>MS_Asis: GET /api/asistencias/resumen?cursadaIds={id}
        MS_Asis-->>Core: {porcentaje, estado}
        alt estado == SIN_REGISTROS
            Core-->>Gateway: 400 "No hay asistencias registradas"
        else
            Core->>MS_Notas: GET /api/calificaciones-parciales?cursadaId={id}
            MS_Notas-->>Core: parciales
            alt estado == NO_REGULAR (< 70 %)
                Core->>Core: condicion = LIBRE (motivo: asistencia)
            else parciales != 3
                Core-->>Gateway: 400 "Faltan parciales"
            else promedio < 4
                Core->>Core: condicion = LIBRE (motivo: promedio)
            else promedio 4 a 6,99
                Core->>Core: condicion = REGULAR
            else promedio >= 7 y modalidad PROMOCIONAL
                Core->>Core: condicion = PROMOCIONADA
            else promedio >= 7 y modalidad FINAL
                Core->>Core: condicion = REGULAR
            end
            Core->>DB_Core: UPDATE cursada SET condicion_final, nota_cierre
            Core-->>Gateway: 200 OK (CondicionPreviewResponse)
        end
    end
    deactivate Core
    Gateway-->>Next: respuesta
```

`GET /api/v1/cursadas/{id}/condicion-preview` ejecuta el mismo cálculo sin guardar. Si `ms-asistencias` no responde, el Core devuelve 503 (`AsistenciasClient`). `NotasClient` no traduce la caída de `ms-notas`, que llega como error genérico.

## 3. Nota de mesa de examen y cierre del acta

Los finales no pasan por la cursada: se registran por mesa en `ms-notas` (`CalificacionMesa`) y el Core los consolida al cerrar la mesa.

```mermaid
sequenceDiagram
    autonumber
    actor Tribunal as Profesor / Administrativo
    participant Next as Next.js (Server Action)
    participant Gateway
    participant MS_Notas as ms-notas
    participant Core as Core (MesaExamenServiceImpl)

    Tribunal->>Next: Carga nota (o ausente), libro y folio
    Next->>Gateway: POST /api/v1/notas/mesas
    Gateway->>MS_Notas: POST /api/notas/mesas
    activate MS_Notas
    MS_Notas->>MS_Notas: RoleGuard + sin nota previa del alumno en la mesa (si no, 409)
    MS_Notas->>Core: GET /api/mesas-examen/{id} (JWT interno de 60 s)
    Core-->>MS_Notas: estado de la mesa
    alt mesa CERRADA
        MS_Notas-->>Gateway: 400 "La mesa se encuentra cerrada"
    else mesa PROGRAMADA
        MS_Notas->>MS_Notas: save(CalificacionMesa)
        MS_Notas-->>Gateway: 201 Created
    end
    deactivate MS_Notas

    Tribunal->>Next: Clic en "Cerrar acta"
    Next->>Gateway: POST /api/v1/mesas-examen/{id}/cerrar
    Gateway->>Core: POST /api/mesas-examen/{id}/cerrar
    activate Core
    Core->>MS_Notas: GET /api/notas/mesas?mesaExamenId={id}
    MS_Notas-->>Core: calificaciones de la mesa
    loop cada InscripcionMesa
        Core->>Core: notaDefinitiva = nota (null si ausente)<br/>aprobado = nota >= 4
    end
    Core->>Core: mesa.estado = CERRADA
    Core-->>Gateway: 200 OK
    deactivate Core
```

## Reglas de diseño

- **Separación de responsabilidades:** `ms-notas` almacena las notas (parciales y de mesa). El Core es dueño de las reglas académicas (promedio, modalidad, condición) y orquesta los cierres. `ms-asistencias` calcula la regularidad por asistencia.
- **Cursada y materia son cosas distintas:** el cierre de cursada da solo `LIBRE`, `REGULAR` o `PROMOCIONADA`. La aprobación por final queda en `InscripcionMesa.aprobado`, y la cursada no cambia.
- **Acta cerrada = inmutable:** `ms-notas` consulta el estado de la mesa al Core antes de crear o editar una nota.
- **Seguridad entre servicios:** cuando el Core llama a un MS, manda directamente el header `X-User-Roles: ADMIN` (sin JWT: el MS confía en ese header igual que con el Gateway). Cuando un MS llama al Core, firma un JWT interno de 60 segundos (`InternalTokenService`) con el secreto compartido.
- **Acoplamiento:** estas llamadas sincrónicas en ambos sentidos son la deuda #22 de [`pendientes.md`](./pendientes.md).
